## It would fail if the boundaries were removed

Reasoning from the code alone; I edited nothing.

- `expectRestricted` (lines 27-31) filters messages to `ruleId === 'no-restricted-imports'` with
  severity 2 and requires at least one. If the src/core or src/data block were removed, or its
  `files` glob stopped matching, there would be no such message and every `rejects …` test in
  that `describe` would fail.
- **Narrowing the glob is caught.** The virtual paths are nested (`src/core/math/__boundary__.ts`),
  so changing `src/core/**/*.ts` to `src/core/*.ts` would also make the tests fail.
- **Removing single patterns is caught.** For src/core: the `phaser` group is guarded by lines
  42-51, the `@game`/`@platform` group by 53-65, and the relative group by 67-76. For src/data:
  `phaser`, `@game` and `@platform` are blocked only by the regex pattern, so removing that regex
  fails three tests. The relative group is guarded by 101-110.
- **Downgrading to a warning is caught.** `severity === 2` means `'warn'` would fail the test.
- **Ignoring the files is caught.** If src/** were added to the ignores, `warnIgnored: true`
  turns that into a "File ignored" warning with no rule id. `expectRestricted` would then fail,
  and `expectClean` requires zero messages, so it would fail too. The comment at line 34 says so.
- **Over-blocking is caught.** The two `accepts …` tests fail if the config starts blocking
  `@core/types`.

### Minor

**m1. The "src/data imports only from @core" half is only tested for phaser/@game/@platform.** (owner: core-dev)
boundaries.test.ts:80-117. The data regex also blocks arbitrary npm packages and Node built-ins
(the T1 probe confirmed `lodash` and `node:fs` are blocked), but no test pins that down. If the
regex were loosened to a deny-list of phaser/@game/@platform, every test would still pass and
`import _ from 'lodash'` in src/data would be allowed.
Fix: add `rejects a third-party package` (e.g. `'lodash'`) and `rejects node built-ins`
(`'node:fs'`) to the src/data describe.

**m2. Allowed data-to-data imports are not tested.** (owner: core-dev)
boundaries.test.ts:112-116. Only `@core/types` is checked as clean. If the regex were tightened
by mistake, `@data/classes`, `./missions/m01` and `../core/types` (from `src/data/missions/`)
could all become errors without any test failing, and the first real data file in M4 would hit
an unexplained lint error.
Fix: add an `accepts …` case for `@data/…` and for a relative sibling import (`./spells`).

**m3. Core-to-@data and core-to-app are not tested.** (owner: core-dev)
eslint.config.js blocks `@data/*` and a relative `../../app/…` from src/core (T1 probe confirmed
both). These are implied by §7.3 (dependencies point down), but there is no test for either.
Fix: add one `rejects` case each.

**m4. Follow-up from M1-T1 (m1-m3).** (owner: core-dev, after game-dev's config fix)
When game-dev closes the T1 gaps (dynamic `import('phaser')`, DOM/`node:*` in core, `../main`),
add one regression case for each here. Each new case has to use a rule id other than
`no-restricted-imports` (`no-restricted-syntax`, `no-restricted-globals`), so `expectRestricted`
will need a `ruleId` parameter.

### Nit

- boundaries.test.ts:14 `{ languageOptions: { parserOptions: { projectService: false } } }`
  repeats what `disableTypeChecked` already sets (`projectService: false`). It does no harm and
  makes the intent explicit, so keeping it is fine.
