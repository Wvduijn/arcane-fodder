## Findings

### Blocker
None.

### Major
None.

### Minor

**m1. A save from a newer version is read as V1 and will be overwritten as V1.** (owner:
core-dev, with game-dev for T9)
`migrate({ version: 7, … })` keeps the V1 fields and drops the rest. That's right for reading.
But the first `appendFallen` → `serializeSave` then writes `version: 1` over a V7 save, losing
the newer fields for good. This can't happen in the MVP (no downgrades ship), but it's the classic
versioned-save trap, and the fix is cheap now. Fix: have `parseSave`/`migrate` report the source
version (or expose `readVersion(raw)`), and have T9's repository refuse to write when the stored
version is greater than `SAVE_VERSION` (log once, keep the game playable in memory). One test:
reading V7 and then saving doesn't overwrite.

### Nit

**n1. Hat Hill entries for a mission id that leaves the union are dropped on load.** (owner:
core-dev / producer at M7)
`MISSION_IDS` is the allowlist, so if M7 replaces `'dev-arena'` with `'m01-goblin-woods'` in
`MissionId`, every M6 test volunteer silently leaves the hill. That's probably fine (dev data), but
it should be a decision, not an accident. Either keep `'dev-arena'` in `MissionId`, or note in the
M7 contract change that dev-arena entries are dropped (or mapped) by `migrate`.

**n2. Hat Hill grows without bound.** Around 80 bytes per entry against about 5 MB of
localStorage is tens of thousands of hats, so this is no MVP concern. Just mentioning it for the
post-MVP Hat Hill screen.
