## Findings

### Blocker / Major
None.

### Minor

**m1. The bus contract has no repeatable test.** (owner: game-dev, with core-dev for the test; D1/D5)
Every system from M4 on will depend on these semantics (once/off, a dead bus throwing on subscribe,
the total count), but the only proof is a scratchpad script that isn't in the repo or in CI. The bus
imports Phaser, and Phaser can't load under `environment: 'node'` (`window is not defined`). Using
jsdom or importing `eventemitter3` directly would each need a new dependency.
Fix (recommended): make the bus Phaser-free. A `Map<GameEventName, Set<listener>>` plus a once-wrapper
map is about 40 lines and uses only the language. It can stay in `src/game/bus/` (it's game wiring,
typed over a game contract). core-dev then adds `tests/game/bus/EventBus.test.ts`, which ports the
checks from `t7.mjs` above. Nothing in the tooling stops tests from importing `@game`. If game-dev
prefers to keep the Phaser emitter, record the browser probe as the bus's test in the M3 gate and
revisit in M4. Either way it isn't a PASS blocker. The producer decides whether it fits in M3.
Behaviour to preserve if it's rewritten: removing a listener during `emit` must not skip the next
listener (eventemitter3 iterates over a snapshot today).

**m2. The "systems off their own listeners" invariant is claimed but not enforced.** (owner: game-dev; D5)
EventBus.ts:13 and MissionScene.ts:55 say systems remove their listeners in `destroy()` before the bus
goes. But `destroy()` silently clears whatever is left, so a system that forgets `off()` is invisible.
And `busListeners` only ever counts the new run's bus, so the restart check can't see it either. There
is no real leak today, because the dead bus and its closures are collected together. It becomes one
the moment any system subscribes through a longer-lived emitter, or keeps a reference to the bus.
Fix: in `destroy()`, when `import.meta.env.DEV` is set and `listenerCount() > 0`, `console.warn` the
remaining event names. The gate's console capture then catches a forgotten `off()`. Alternatively,
drop the claim from both comments.

### Nit

**n1. A widened event name type defeats payload checking.** EventBus.ts:41. If the caller's event
variable has type `GameEventName` (for example, a table of events to forward), `K` becomes the union
and any payload of any event type-checks. That's harmless with literal event names. If forwarding ever
appears, a `{ [K in GameEventName]: [K, GameEvents[K]] }[GameEventName]` tuple signature closes it.

**n2. A throwing listener aborts the rest of that emit**, and the error propagates into the scene's
`update`. That's acceptable fail-fast behaviour in dev. Worth one line in the class doc so M4 systems
don't assume isolation.

## Answer to the producer's question (unit tests)
The browser verification is enough for an M3 PASS: the bus is small, I reproduced the behaviour
independently, and D1 only asks for unit tests on core logic. It isn't enough long-term, because the
bus becomes the backbone of every M4+ system and its proof isn't in CI. I recommend m1's pure-TS
rewrite plus a core-dev test, either in M3 if there's slack or as the first M4 task, before more
subscribers pile on.
