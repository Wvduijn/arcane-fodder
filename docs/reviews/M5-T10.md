## Verdict: PASS

SpellSystem is a thin shell over core:
- **Slots.** Derived on every read through a memoised reader that is created per scene run, so a
  restart can't emit a stale `spell:lost`. `spell:lost` comes from a diff of two derivations,
  re-derived on `unit:died` as well, so it fires on the frame the last caster fell.
- **Casting.** Uses only `GameInput.aimWorld` and core `castSpell`. Cast ids come from the scene's
  shared `IdAllocator`, the same one squad, enemies and kegs use.
- **Impacts.** Every impact is one `CombatSystem.resolveArea` call with `teams: ['enemy']`.
- **Fireball bodies.** Fireball explodes on living enemies plus kegs (`solidOnly`, so a fusing keg
  still stops it).

SpellFxView is pooled throughout and only reads state:
- **Fireball:** a 15 px orb with an ember trail, and a burst that fills exactly the data radius.
- **Lightning:** a ~20 px reticle that shrinks over the telegraph, then a bolt from the top of the
  view plus a ground flash.

FX colours mirror the style-guide hexes exactly (checked all 12 against style-guide §4). I
measured D2 and D3 in the game myself.

### Nit

**n1. The Fireball burst core asks the flash budget; the Combust pop's identical core doesn't.** (owner: game-designer to decide, game-dev to apply)
SpellFxView treats the Fireball burst's `flame-white` core as an impact flash (`tryFlash`).
ReactionFxView draws the same core for every Combust pop without asking (ReactionFxView.ts:162),
following §5's "no screen flash" for Combust. Both are defensible. They should follow one rule,
though: either a near-white burst core counts toward §1.9 or it doesn't. With ~5 Combusts/s today,
the answer matters for flash safety. Ask game-designer to write the rule into readability §1.9 or
§5; game-dev aligns the code.

## Re-check addendum (2026-10-19)

**n1 closed** (with M5-T11.md n2). The rule is in readability §1.9: a near-white area of radius
≥ 16 px (logical) counts as an impact flash. game-dev made the code follow the size rather than
per-call decisions:
- `FlashBudget.tryFlash(nearWhiteRadiusPx)`: below `minFlashRadiusPx: 16` it returns true and
  doesn't count; at 16 or more it applies the 3-per-1000 ms cap. The module comment cites §1.9 and
  the CD exemptions (hit flash, keg blink).
- `bursts.ts` `burstCoreRadiusPx(r) = r × 0.4`, the same band `drawBurst` fills.
- Fireball asks with 17.6 (counted). The Lightning ground flash asks with its real core, 5 px
  (never counted). In ReactionFxView.ts:184, Kaboom asks with 28.8 (counted) and Combust with 12.8
  (never counted).
- A skipped core leaves the burst in its edge colours.

Reading the code, the sizes match readability §5 and §1.9. game-dev's in-game numbers under WebGL:
- no-input fight: 4 Combusts with budget 0/0;
- two Lightning ground flashes: played, budget 0/0;
- keg chain: granted 3, refused 1.

These agree with my T11 chain measurement. I'll repeat the in-game flash check at the gate on the
final build. Re-run: typecheck 0, lint 0, `Tests 673 passed (673)`.

Verdict: **PASS** (final). The rule is pending producer or CD confirmation as a flash-safety call;
if it changes, this needs a re-check.
