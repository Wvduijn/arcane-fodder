# Review M2-T5 — CameraController

Reviewer: reviewer · Date: 2026-10-14 · Owner of task: game-dev
Scope: src/game/world/CameraController.ts, and the update order and wiring in
src/game/scenes/MissionScene.ts.

## Verdict: FAIL

The follow logic itself is good:
- The bounds clamp is mathematically identical to Phaser's, so it holds at any zoom.
- The smoothing is frame-rate independent to within 1.4 px.
- The snap at start works.
- The update order is input → leader → camera.

But `destroy()` crashes on every scene shutdown. Phaser destroys the camera before
MissionScene's SHUTDOWN handler runs, so `camera.removeBounds()` dereferences a null `_bounds`.
The exception aborts the rest of `handleShutdown`, so the input never gets destroyed, and the
scene **never restarts**: it stays in status SHUTDOWN. I reproduced this in headless Chrome. It
blocks T6's restart check and D4/D5 at the gate. The fix is one line.

## Producer's three points

### Frame-rate independence: holds, within 1.4 px

- **Target standing still:** `dampFactor` is exact here (M2-T2 tests: 2 × 8 ms = 16 ms, and 30 fps =
  144 fps over 1 s). Settling after a stop is the same at every frame rate.
- **Target moving:** exponential smoothing toward a *moving* goal leaves a steady-state lag of
  `v·dt·(1−t)/t`, and that lag depends slightly on dt. That's inherent to the method; it isn't a bug
  here. At 110 px/s and a 90 ms half-life it comes to **12.53 px at 30 fps, 13.39 at 60, 13.90 at 144**,
  with a continuous-time limit of 14.28. A simulation of 2 s of running right gives scroll 159.47 /
  158.61 / 158.10 at 30 / 60 / 144 fps: a **1.4 px** spread between 30 and 144 fps, which is below
  one placeholder texel at ×3. Acceptable. No fixed per-frame lerp anywhere, as the sprint requires.
- **Deadzone path:** the goal is pushed by the deadzone on the current target sample. That's a
  per-sample push, so 30 and 60 fps can't differ by more than one frame of movement (≈ 3.7 px at
  30 fps), and the easing smooths it out. Fine.
- dt ≤ 0 gives t = 0 (no move). A long frame gives t → 1 (snap to goal). Both are sane.

### Scroll never leaves [0, world − view], at any zoom: holds (by construction)

- `clampScrollX/Y` (:77-87) is term for term the same as Phaser's `clampX` (BaseCamera.js:968-987):
  `min = bounds.x + (displayWidth − width)/2`, `max = max(min, min + bounds.width − displayWidth)`,
  with `displayWidth = width / zoomX`.
- The goal is clamped each frame (:59-60), and the start scroll is clamped (:34-36).
  `lerp(current, goal, t)` with t ∈ [0, 1] stays between two in-range values. On top of that,
  Phaser's own clamp runs in `preRender` because `setBounds` is set (:29).
- At zoom 1 with the 640×360 view (Scale.FIT doesn't change the internal size at any window size),
  this is exactly `[0, 1408] × [0, 1176]` for DEV_ARENA.
- A world smaller than the view pins to `min` (left/top aligned), the same as Phaser. Space outside
  the map is unavoidable in that case. It isn't reachable with any map in the plan.
- **Note for my gate (G):** at zoom ≠ 1, `scrollX` isn't the visible left edge. The gate should
  assert on `camera.worldView` being inside the world rect, not on raw scroll, so the check stays
  correct if zoom is ever used.

### Nothing leaks on destroy (removeBounds): FAILS, see B1

`CameraController` registers no listeners, so the only thing it could leak is the bounds state.
The camera itself is destroyed and recreated by `CameraManager` on every SHUTDOWN/START
(CameraManager.js:179-203, :726-741), so bounds can't leak across a restart anyway. And the
`removeBounds()` call is what crashes.

## Findings

### Blocker

**B1. `CameraController.destroy()` throws on scene shutdown, so the scene can't restart.** (owner: game-dev)
CameraController.ts:69-71, together with MissionScene.ts:32 and :40-45.
`CameraManager.start` registers its `once(SHUTDOWN)` during `sys.start()` (START), before
`MissionScene.create()` registers `handleShutdown`. eventemitter3 calls listeners in the order
they were registered, so by the time our handler runs, `camera.destroy()` has already set
`_bounds = null` (BaseCamera.js:1641), and `removeBounds()` → `this._bounds.setEmpty()` throws.
Effects: `gameInput.destroy()` (MissionScene.ts:43) never runs, `systems` is never cleared, and
the restart stops halfway (scene stuck in SHUTDOWN).
Fix: tolerate an already-destroyed camera, e.g.
```ts
destroy(): void {
  // At scene SHUTDOWN, CameraManager has already destroyed the camera (and its bounds).
  if (this.camera.scene) this.camera.removeBounds();
}
```
(`BaseCamera.destroy` sets `scene = null`, :1643.) Alternatively, drop `removeBounds()` and say
in a comment that Phaser recreates the camera. The guard is better, because it also works if a
controller is ever destroyed in the middle of a scene.
Regression check: T6's restart key, plus my gate's ×10 restart probe. There's no unit test,
because tests can't import Phaser code under §7.3.

### Major
None.

### Minor

**m1. One throwing `destroy()` skips every teardown after it.** (owner: game-dev)
MissionScene.ts:40-45. B1 shows the failure mode: one exception and the input listeners leak.
Fix: once B1 is fixed, document in System.ts:1 that "at SHUTDOWN, Phaser's cameras, display list
and input plugin may already be torn down; destroy() must tolerate that". Optionally, make
`handleShutdown` destroy each system inside `try/finally` so the input is always released. The
documentation is the important part. Wrapping would hide bugs like B1 if the error isn't
re-thrown, so if you wrap, re-throw after cleanup.

**m2. The deadzone is in world pixels, but the name says "Px" with no unit context.** (owner: producer, contract)
`deadzoneWorld` (:40-48) uses `deadzoneWidthPx` as world pixels. At zoom 1 that's the same as
screen pixels in the 640×360 view, so nothing is wrong today. If zoom is ever used, the designer's
"15% of the view" turns into a different screen fraction. Fix: say "world px" in the
`CameraTuning` doc comment, or divide by zoom here. The comment is enough while zoom is fixed at 1.

### Nits
- `Positioned` is still imported from LeaderController.ts (:6). M2-T4 suggested moving it. Now that
  the camera depends on it, this is the right moment.
- Order: input → leader → camera (MissionScene.ts:31, :35-37), so the camera reads this frame's
  leader position. That's correct. And the camera never uses `startFollow`, so Phaser's internal
  follow lerp can't fight it.
- Known and accepted, not counted here: the top-edge sprite clipping (producer's M7 log) and the
  bottom edge (T4 M1). `LeaderController` still has no `setOrigin`, so T4 M1 is still open.
