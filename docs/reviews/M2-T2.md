## Producer's decisions

| Decision | Assessment |
|---|---|
| `stepPosition` returns the position unchanged when dt ≤ 0 | OK. A paused or zero-dt frame must not move the leader. It returns a copy, not the same object, which keeps "no shared mutable state" (movement.ts:17) |
| `dampFactor` returns 0 when dt ≤ 0, even if halfLife ≤ 0 | OK. "No time passed, so no movement" beats "snap" because otherwise a zero-dt frame would teleport the camera. The order is documented (smoothing.ts:6) and tested (smoothing.test.ts:51-53). Consequence for T5, below |
| Analog input longer than 1 is normalised | OK. The sprint says "length ≤ 1" and plan §6 says `moveVector` is "length 0..1". Clamping only above 1 keeps analog magnitudes under 1 for the M8 joystick (movement.test.ts:35-48) |

### Nits (owner: core-dev, optional)
- **n1.** movement.ts:21-24. `clampToRect` assumes `rect.x`/`rect.y` is the top-left corner
  (`max = start + size - inset`), and the tests at movement.test.ts:96-128 confirm it. The `Rect`
  contract doesn't say this yet (M2-T0 m1, producer). Once the producer clarifies `Rect`, nothing
  changes here. If the contract stays silent, add "rect is top-left based" to this doc comment.
- **n2.** movement.ts:16. `stepPosition` trusts `move` to have length ≤ 1. That's correct by
  design (callers go through `moveVectorFromAxes`), but one sentence in the doc comment ("`move`
  is expected to come from `moveVectorFromAxes`") would stop a later caller from passing raw axes.
- **n3.** A negative `insetPx` widens the allowed area, and a NaN axis passes through
  `moveVectorFromAxes` as NaN (`NaN > 1` is false). Neither can happen with the current callers
  (data radius 10, keyboard axes in {-1, 0, 1}), so a guard isn't worth it. I'm just recording them.

### Notes for game-dev (T4/T5), not T2 defects
- With `dampFactor(…, 0) === 0`, the camera won't move on a zero-dt frame. T5 should therefore
  place the camera on the leader at create time (center on the target once) and not rely on
  damping from scroll (0, 0). Otherwise the first frames show a visible pan from the top-left
  corner.
- T4 must normalise through `moveVectorFromAxes` *before* `stepPosition`, then call
  `clampToRect(…, MOVEMENT.wizardBodyRadiusPx)` after each step, as the sprint says. I'll check
  this in the T4 review.
