## Findings

### Blocker
None.

### Major

**M1. Debug kills (K, L) leave the wizard alive in `CombatWorld`.** (owner: game-dev; D4, D7)
DebugOverlay.ts:691 and :698 call `squad.kill([debugDeath(id)])`. `SquadSystem.kill` removes the member
and emits `unit:died`, but no one marks the unit dead in `CombatWorld` (only
`CombatSystem.flushDeaths` → `world.remove` does that, for combat deaths). Consequences, from the code:
- `CombatSystem.bodies()` (CombatSystem.ts:272-288) still lists the wizard as a live body at its
  `fallen` position (`SquadSystem.positionOf` falls back to `fallen`), so an arrow crossing that spot hits
  a dead wizard and emits `unit:damaged` for it. That breaks D4, and the debug counter
  `damagedAfterDeath` would catch it.
- `HealthBarView` draws a bar at the fallen spot for a debug-killed wizard that was below full HP
  (HealthBarView.ts:56-62).
- The debug snapshot reports the dead wizard as `alive: true`, which misleads the gate's D4 checks.
- It's the "two authoritative states" smell CLAUDE.md rules out: squad membership says dead, combat
  state says alive.

Fix: route debug kills through combat state, e.g. `CombatSystem.kill(id, cause)` that calls core
`killUnit(world, id, cause)` (it already returns `combat`/`blood`/`false`, M4-T3) and queues the record
for `flushDeaths`, so the wizard dies through the same `SquadSystem.kill` + `world.remove` path as a
combat death, on the next flush. Add a small test or a debug assertion that, after K,
`combatWorld.isAlive(id)` is false.

### Minor
None.

### Nit

**n1. `diedIds` in the overlay grows for the whole run** (DebugOverlay.ts:282). Debug only, cleared on
restart. Fine.

**n2. G spawns relative to the original spawn, not the current leader.** EnemyAiSystem `origin` is
captured at scene start. That's fine for the dev check (the archers stay where the playtester expects
them), and noted so nobody is surprised.
