## Producer's four points

### (1) Every action in plan §6 is mapped: OK

| §6 action | Binding | Evidence |
|---|---|---|
| Move squad: WASD / arrows | W/UP, S/DOWN, A/LEFT, D/RIGHT → `moveVectorFromAxes` | KeyboardMouseInput.ts:11-16, :107-109 |
| Aim: mouse position | `POINTER_MOVE` and `POINTER_DOWN` store the screen point; `update()` projects it | :85-86, :111-120, :142-150 |
| Spell 1: Q or left click | Q; button 0 | :19, :30 |
| Spell 2: E or right click | E; button 2 (`disableContextMenu: true` is set in src/app/config.ts:18) | :20, :31 |
| Convergence: R or Space | R, SPACE | :21 |
| Volunteer!: F | F | :22 |
| Pause: Esc / P | ESC, P | :23 |

`ACTION_KEY_BINDINGS` is typed `Record<InputAction, …>`, so adding a new `InputAction` without
binding it is a compile error. Movement goes through T2's `moveVectorFromAxes`, which means the
diagonal is normalised and opposite keys cancel to 0.

### (2) consume() is edge-triggered: OK

- `Key` emits `DOWN` once per physical press. `emitOnRepeat` defaults to false (`addKey` :494,
  `Key.onDown` :289-293), so holding a key or OS auto-repeat doesn't fire again.
- The listener adds the action to `pending`. `update()` replaces `ready` with `pending` and clears
  `pending` (:103-105). `consume()` is `ready.delete` (:99), so it's true at most once.
- A press and release inside one frame is still caught, because the press is buffered.
- An action that isn't consumed in the frame after its press is dropped at the next `update()`,
  so there's no stale Space press that fires Convergence seconds later. That's the right behaviour
  for "true only on the frame the action was requested".
- Window blur: the keyboard plugin calls `resetKeys` on `GameEvents.BLUR` (:224), so held movement
  keys don't stick after alt-tab.

The class comment (:36-42) says `update()` must run once per frame before any reader. I'll check
in T4 that MissionScene calls it first.

### (3) destroy() removes every key and pointer listener: OK

- Both pointer handlers are stable arrow-function fields, and `off` uses the same references
  (:124-125).
- Every key created here gets `removeAllListeners()`, then `removeKey(key, true, true)`, which
  destroys the key and releases the capture (:126-130). Internal state is reset too.
- It's safe in either order with Phaser's own `KeyboardPlugin.shutdown` (:880-893, `removeAllKeys(true)`):
  if the plugin goes first, `removeKey` finds nothing (`indexOf` → -1) and does nothing.
- A real restart-leak count (×10) belongs to T6 and the gate, once the scene wiring exists. See m1
  for the one case where `destroy()` removes too much.

### (4) The one-frame aimWorld lag: acceptable, keep it as is

How it works: `getWorldPoint` inverts `matrixCombined`, which `Camera.preRender` rebuilds only
inside `CameraManager.render`. During `update()`, the matrix is therefore the one used for **the
frame currently on screen**.

1. **This is the correct target.** The player aims at what they see. The last rendered matrix maps
   the cursor to exactly the world point under it in the displayed image. Using the current
   (post-update) scroll would aim at a point the player hasn't seen yet. Calling this a "lag"
   overstates it: compared with the displayed frame the error is 0, and compared with the
   not-yet-rendered scroll it's one frame of camera motion.
2. **It doesn't touch the M5 Verify.** GDD mvp.md:207 checks "at 4 camera scroll positions (map
   corners)". At a map corner the camera is clamped to its bounds and stationary, so the frame
   delta is 0 px whatever the timing.
3. **Size while the camera moves.** The camera can't move faster than the leader (110 px/s), plus
   brief catch-up after the deadzone. That's about 1.8 px at 60 fps and 3.7 px at 30 fps. On a
   long frame hitch (a 100 ms dt clamp) it could reach about 11 px. Even then, the spell lands
   where the player saw the cursor.
4. **Rounding.** `preRender` builds the matrix from the unrounded `scrollX/Y` (Camera.js:614-631),
   and `pixelArt` rounding happens at draw time. The mismatch with the displayed pixels is at most
   0.5 px, well inside 2 px.

**Recommendation:** don't change it. When the M5 aim test is written, have it compare against the
world point under the cursor *in the displayed frame*, and add one case with the camera moving, so
any future change to this timing is caught. Keep the comment at :111-112. It's accurate and it's
the reason this review exists.

Before the first render the matrix is identity, so `getWorldPoint` would return screen
coordinates. That can't happen in practice, because `pointerScreen` stays null until a pointer
event, and pointer events need a displayed canvas. No action needed.

### Minor

**m1. `destroy()` can destroy keys and listeners owned by other systems.** (owner: game-dev)
KeyboardMouseInput.ts:126-130. `KeyboardPlugin.addKey` returns the **existing** `Key` when that
key code is already registered in the scene (KeyboardPlugin.js:526-538). Any later system that
does `addKey(ESC)` (a pause menu), `addKey(SPACE)` or `addKey(P)` gets the same object. Then this
`destroy()` calls `removeAllListeners()` on it (dropping the other system's handlers) and
`removeKey(…, destroy=true)` (killing the key under it). Today this is harmless: T6's backtick
doesn't overlap. It becomes a silent bug when a pause overlay or the M6 debug keys arrive.
Fix: keep the handler references and remove only your own, e.g. store `[key, handler]` pairs and
call `key.off(Phaser.Input.Keyboard.Events.DOWN, handler)` in `destroy()`. Then either drop the
`removeKey` call and let `KeyboardPlugin.shutdown` remove the keys at scene SHUTDOWN, or remove
only keys that `listenerCount(DOWN) === 0` afterwards. Polled move keys have no listeners, so
the plugin's shutdown is enough for them.

**m2. The edge-trigger buffer has no automated test.** (owner: game-dev, with core-dev for the test)
The pending→ready→consume logic (:47-50, :98-105) is the part of D4 that is easiest to break
without noticing (for example by swapping the clear order). It is pure: two `Set`s and no Phaser.
Fix: extract it into a small Phaser-free `ActionBuffer` (`press(action)`, `advance()`,
`consume(action)`), placed where §7.3 allows a test to import it, and have core-dev add tests for:
consume is true once only, a press is invisible until `advance()`, an unconsumed press is dropped
after one more `advance()`, and a press plus release in the same frame still counts. The
automated playtest at the gate also covers it, but end-to-end only.

### Nits
- On a touch device, a tap arrives as `button 0`, so this adapter would treat every tap as
  spell1. That's expected (touch is M8's `TouchInput`), but the adapter choice in M8 must not fall
  back to `KeyboardMouseInput` on touch-only devices.
- `update()` allocates a new `aim` object each frame (:119). That's negligible now and consistent
  with the immutable `Vec2` style. Leave it.
