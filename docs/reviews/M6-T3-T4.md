unchanged (the existing reactions tests still pass).

### Minor

**m1. No test runs the real `src/data/convergences.ts` through `resolveCombo`.** (owner: core-dev)
The rule tests use fixtures on purpose (fixtures.ts:1-4), and that's right. But D1 and plan §9
say *each MVP combo* resolves correctly for every composition, and nothing pins the shipped data
to that table. If the designer changed Firestorm's priority to 1, the tie rule would still pick
Firestorm. If they dropped `'storm'` from its `requires`, or keyed the data wrong, no test would
fail until T8's sims. The data also has a different shape from the fixture (a record keyed by id,
so the call site needs `Object.values(CONVERGENCES)`). Fix: one `it.each(COMPOSITIONS)` in
combo.test.ts against `Object.values(CONVERGENCES)` and `CONVERGENCE.scaling` from `@data/...`. It
asserts combo id and power only, so retuning damage or radius never breaks it.

**m2. Prettier drift in two test files.** (owner: core-dev)
`tests/core/convergence/fixtures.ts:61` (Firestorm bolt blast object) and
`tests/core/combat/reactions.test.ts:215` (`setup([...])` call) are over the print width. `pnpm
lint` doesn't run Prettier, so the gate doesn't catch it. Fix: `pnpm exec prettier --write` on
those two files.

**m3. The `reactionSourceId` test checks the spread Burning only, not the Combust damage.**
(owner: core-dev)
reactions.test.ts:196-221 asserts the spread status's `sourceId`. The meter charges from
`unit:damaged.source`, though, so the load-bearing part of Q3 is that the Combust **hits**
(origin and neighbours) carry `REACTION`, and the bolt's own hit still carries `STRIKE`. Fix: also
assert on `r.reactions[0].area.hits` sources (all `REACTION`) and on `r.area.hits` (all `STRIKE`).

### Nit

**n1. `lastSource` is never pruned for enemies that never die.** (owner: core-dev)
It's bounded by enemies hit per run and the meter is recreated per run, so this is fine for the
MVP. Worth one line in the API doc so T10 doesn't keep a meter across restarts.

**n2. Refreshed Burning changes who gets credit (M6-T0 note).** (owner: core-dev)
This is covered implicitly: the meter keys on whatever source the tick carries, and
`applyStatus` replaces it on refresh. So the meter is correct for any applier. The "last applier
owns it" behaviour is tested in status tests, not here. No action unless you want an explicit
case.
