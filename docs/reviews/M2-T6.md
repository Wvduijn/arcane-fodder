### Minor

**m1. Key auto-repeat crosses a restart: holding Backspace restarts the scene once per repeat, and a held action key fires one phantom press after a restart.** (owner: game-dev)
DebugOverlay.ts:113-116 and :212-214; KeyboardMouseInput.ts:79-83.
Mechanism (Phaser 4.2.1 `Key.onDown`, Key.js:263-293): `DOWN` is emitted when `!this.isDown`.
`KeyboardPlugin.shutdown` destroys every Key on restart, and the new scene's `addKey` creates a
fresh Key with `isDown = false`. So the next OS auto-repeat `keydown` (`event.repeat === true`)
counts as a first press. Probe C: 16 restarts from one held Backspace. The same path means a
Space/R/Q/E/F/Esc/P held through a restart buffers one action press in the new scene (one
phantom Convergence/spell/pause). That's harmless in M2, but from M5 on it would mean a cast
nobody asked for.
Fix: ignore repeats in both handlers. Phaser passes `(key, event)` to `DOWN` listeners:
```ts
private readonly restart = (_key: Phaser.Input.Keyboard.Key, event: KeyboardEvent): void => {
  if (!event.repeat && this.visible) this.options.onRestart();
};
```
Do the same in `KeyboardMouseInput`'s action handler (`if (!event.repeat) this.actions.press(action)`)
and in `toggle`. A real first press never has `repeat` set, so this can't drop a legitimate press.
Movement keys are polled through `isDown`, and there a repeat re-arming a held W after a restart
is the desired behaviour, so leave them alone.

### Nits (owner: game-dev, optional)
- With `?debug` the overlay starts visible, so Backspace restarts during normal debug play. It's
  bound to nothing else and debug-only, so that's acceptable. Just know that it's the most likely
  cause of a "surprise" restart for a human tester using `?debug`.
- The crosshair uses `aimWorld` from the last-rendered matrix (M2-T3 point 4), but it's drawn
  after this frame's camera move. While the camera moves it therefore sits about 1-2 px off the OS
  cursor. At map corners the camera is still, so the gate's crosshair check is unaffected. This is
  an observation, not a defect.
- `overlaysCreated/overlaysLive` are module-level, so a Vite HMR full reload resets them. That's
  fine for the restart probe, and worth knowing when you read them.

## The unexplained shutdown game-dev saw: most likely caused by my T5 probe

I couldn't reproduce a spontaneous shutdown with the current build (probes A-E, no repeats except
in C). But the scratchpad timestamps point at my own T5 probe:
- `restart-probe.mjs` launched headless Chrome with remote debugging on **port 9333** at
  **21:08:13** (`chrome-prof`). game-dev's `cdp.mjs` also defaults to **9333**, and their
  `dbg.mjs` run started at **21:08:17** (`chrome-zptzQu` at 21:08:21). With two Chromes contending
  for one debugging port, a client that fetches `/json` can attach to the other's page.
- My probe built a second `Phaser.Game` in the page and called `MissionScene.scene.restart()` ×3,
  which threw the B1 `setEmpty` error and left the scene in SHUTDOWN. My Vite log even records
  `21:08:12 [vite] (client) [Unhandled error] TypeError: Cannot read properties of null (reading 'setEmpty')`.
  To anyone attached to that page, it looks like a single unexplained shutdown, and it never comes
  back once the probe stops. That matches "once, not in 4 later runs".
- Also my fault: at the end of the T5 review I ran `pkill -f "vite --port 5199"`. My own Vite had
  failed to start ("Port 5199 is already in use"), so that pkill killed **game-dev's** dev server.
  That fits the restarted servers in `vite.log`, `vite2.log` and `vite3.log` after 21:17.
  This time I didn't start or kill any server, and I used ports 9401-9403.

Recommendation: no code change. For the gate, I'll use a dedicated CDP port range, and I'll only
ever stop processes I started, by PID.
