## Findings

### Minor

**m1. Left-behind runners need a name and class from the caller, and the split can't check that
they were alive** — `portal.ts:125-139`. `extractionSplit` appends every `runners` id to
`leftBehind`, and `buildResult` takes `leftBehind: WizardRecord[]` from the caller. That is
correct, but the documented contract doesn't say the runner list must hold only *living*
runners. A runner that detonated on the same frame (dead, already written to Hat Hill as
`volunteer`) must not also be written as `left-behind`.
Fix: one header line ("pass only runners still sprinting after this frame's deaths") plus a
test, or filter by `isAlive` inside `checkExtraction`. Owner: **core-dev**; game-dev must respect
it in T15/T17.

**m2. A surge order can sit in the queue forever** — `surge.ts:189-192`. While no point is far
enough, a held order is skipped (`i++`). `surgeFinished` stays false until the queue empties. On
m01 that only happens with a wizard within 160 px of every surge point at once, which is
impossible: the points span 1 500 px. So this is harmless here. If game code ever waits on
`surgeFinished` (for music or HUD), document that it can stay false while the squad camps.
Owner: **core-dev** (doc line), FYI **game-dev**.

### Observation

- **o1. The timer starts at control, not at scene start.** GDD §14 says "mission start to end";
  `tickMission` counts only from `beginPlay` (after the 3 s intro pan or its skip). I think that's
  the right reading: the pan isn't play, and on restart it's skipped anyway (sprint "my calls"),
  so the first try would otherwise be 3 s slower. I'm flagging it so the CD sees the
  interpretation. Owner: **main** (confirm with the CD, no code change expected).
- **o2.** Victory and defeat on the same frame: `endMission` keeps the first call. The frame order
  (portal extraction check after deaths) decides which comes first; I will check it live at T18.
