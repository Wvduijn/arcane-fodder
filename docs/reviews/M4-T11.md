## Verdict: PASS WITH NOTES

`StatusSystem` does what M4-T4 m2 asked for. It applies the ticks through `CombatSystem.applyHit` first
(so a tick kill is charred and a second tick on a just-dead unit is a no-op), then emits
`status:expired` only for units still alive, then flushes the frame's deaths once. It owns nothing.
The overlay is pooled, follows the feet, flickers out of phase per id, and is removed on
`status:expired`, on `unit:died` and on despawn (G). It unsubscribes all three listeners on destroy. In
game the overlay appears on hit and is gone after every death. The only gap is that D3's "disappears on
expiry" can't happen in game with current tuning; game-dev already flagged that.

## Findings

### Blocker / Major
None.

### Minor

**m1. D3's in-game "disappears on expiry" can't be shown with current tuning.** (owner: producer, with game-designer; D3)
A fire bolt deals 8 and Burning deals 6 × 3 = 18, so every burning grunt (24) or archer (18) dies before
the status runs out. Game-dev reported this and my runs agree (`status:expired` = 0 in all 3). The expiry
path is covered by core tests (M4-T4) and the overlay's `handleExpired` is a two-line listener, but D3
asks for it in game. Options, the producer's call:
(a) accept code-level evidence for M4 and check it in game in M7, when huts (thatch, more HP) burn;
(b) add a debug-only key that applies Burning to a full-HP *wizard* or a target dummy;
(c) leave it to a tuning change.
I recommend (a), with this note in the gate report.

### Nit

**n1. `SHOWN` is a one-element set** (BurningOverlayView.ts:22). That's fine, and it's where M5+ statuses
will plug in.

**Producer/CD decision on m1 (2026-10-16):** a debug key **B** applies Burning with no damage to the
nearest goblin, so expiry is visible in game in M4. game-dev is adding it; I'll re-review it together
with the M4-T13 M1 fix.
