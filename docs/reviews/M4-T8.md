the sim never kills a wizard, so the "killed by goblins → M3 succession" half of D5 and the
dead-wizard D4 checks go unexercised; and D2's wording needs aligning with Q1 (producer).

### Minor

**m1. No wizard ever dies in the sim, so D5's succession clause and the dead-wizard D4 checks never run.** (owner: core-dev; D4, D5)
In all 9 runs `wizardsLost` is 0 and grunts get only 5–6 swings in. That makes the dead-wizard paths
in the sim (`killSquadMembers` at :145, "dead wizard still in the squad" at :190, wizard fire skipped
when dead at :216, an arrow or swing on a dead wizard) dead code under test. D5 says "a wizard killed
by goblins goes through M3 succession", and D4 needs "dead unit never fires/is hit" for wizards too.
Fix: add a second scenario to encounter.test.ts that forces losses, for example the same sim with the
leader's HP set low before the fight (`world.setHp`), or an `encounter` option with 12 grunts.
Assert ≥ 1 wizard lost, that the leader changed to the next living member (M3 succession), that no
dead wizard fired afterwards, and `violations` = []. It doesn't need to be a no-input *win*.

**m2. D2's "every goblin dead" conflicts with CD Q1's layout.** (owner: producer, M4.md text)
M4.md D2 says the sim and the reviewer's in-game run "both end with every goblin dead". Per Q1 the two
archers are placed out of aggro for the *manual* push check, so with zero input they never die. The
sim (rightly) counts only the 6 grunts (`D2_GROUP`, encounterSim.ts:76) and asserts the archers stay
idle. I agree with core-dev's reading; it's the only one consistent with Q1. The D2 text should say
"every goblin of the D2 pack (the 6 grunts) dead", so the gate isn't judged against an impossible
literal. No code change.

### Nit

**n1. The "dead enemy still stepped" check can't fire.** (owner: core-dev)
encounterSim.ts:203: `handleDeaths` removes dead enemies from `enemies` (:147) before the next
`stepEnemies`, so the check is structurally always true. In the sim, "dead enemies never move" is
guaranteed by removal, which mirrors what the scene will do; `stepEnemies`'s own freeze is covered by
unit tests (M4-T7). Fine, but the comment at :65 overstates what the sim proves. Optional: drop the
check or say "removed on death".

**n2. The sim inherits M4-T4 m1.** Burning is applied in the projectile phase and stepped by the same
frame's dt (:276 then :292), so its first tick is one frame early here too. When core-dev fixes T4 m1
in `status.ts`, the sim picks it up automatically.
