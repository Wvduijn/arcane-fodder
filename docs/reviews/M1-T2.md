### Minor

**m1. `clamp` with `min > max` and NaN input is not tested.** (owner: core-dev)
vec2.ts:31-34. The comment says min <= max is expected, but nothing pins down what actually
happens: `clamp(5, 10, 0)` returns `0` (max wins), and `clamp(NaN, 0, 1)` returns `NaN`. Later
milestones will feed clamp with designer data (ranges in src/data), so a swapped range could show
up there.
Fix: add one test that documents the current behaviour for each case, so a later refactor can't
change it silently. No code change needed.

### Notes (no action needed for M1)

- **Scalar helpers in vec2.ts.** `clamp` and `lerp` take numbers, not vectors. The sprint puts
  them here, so this is correct for M1. When M3 (breadcrumb trail, formation) needs vector
  interpolation, add a `lerpVec(a, b, t)` and consider moving scalar helpers to `core/math/scalar.ts`.
- **Non-finite input.** `normalize({x: Infinity, y: 0})` returns NaN components. That's fine
  for now; keep it in mind if positions can ever overflow.
- **`-0` components.** `scale(v(-9, 9), 0)` gives `{x: -0, y: 0}`. `toEqual(v(0, 0))` would
  fail on that (Vitest treats -0 and 0 as different in `toEqual`), and the test at
  vec2.test.ts:49-51 rightly checks `length` instead. Worth knowing when writing future assertions.
